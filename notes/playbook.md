ReStock AI - Project Playbook1. One-Page OverviewProblemRetail shops lose money by either over-ordering inventory, which leads to waste, or under-ordering inventory, which leads to stockouts.UserThe target user is a store manager or purchasing manager responsible for stock replenishment decisions.SolutionReStock AI predicts a demand range per product and recommends tomorrow's order quantities, accompanied by a plain-language explanation for each recommendation.What We Build FirstWe start by locking a public Kaggle retail dataset, setting up data preprocessing, EDA, feature engineering, establishing a naive baseline, and comparing gradient boosted machine models (LightGBM/XGBoost) with a simple deep learning model using a strict time-based evaluation split.What We Do LaterAfter the core machine learning and deep learning baselines work and official capstone guidelines arrive, we will expand into the product decision layer (converting quantiles to order quantities), SHAP explainability, automated explanations, and a Streamlit/FastAPI application.2. Phase-by-Phase ExplanationPhase 1: Data and Baseline (Nov 6 - Nov 15)Aim: Select a Kaggle dataset, subsample it, clean raw files, construct foundational lag/calendar features, and establish a running baseline model.Why: Instructor guidance requires establishing a complete data pipeline and simple baseline before building complex models.Outputs: the subsample in restockai-work/interim, cleaned and feature files in restockai-work/processed, EDA notebooks, feature engineering script (src/features.py), and baseline result logs (notes/results.md).Pitfalls & Prevention:Data Leakage: Occurs when future information is accidentally included when predicting past or present outcomes. We avoid this by building lag features strictly using past data points.Random Split: Occurs when dataset rows are split randomly across time, leaking future data into training sets. We avoid this by enforcing strict chronological time splits.Phase 2: Machine Learning Models (Nov 16 - Nov 24)Aim: Build one global LightGBM/XGBoost model to generate point and quantile forecasts ($q_{10}, q_{50}, q_{90}$).Why: Tree-based gradient boosting handles tabular demand forecasting efficiently and provides reliable interval predictions without heavy compute costs.Outputs: Trained LightGBM model scripts (src/models/), quantile prediction table (store, item, date, q10, q50, q90), and walk-forward backtest evaluation logs.Pitfalls & Prevention:Quantile Crossing: Occurs when a lower quantile prediction exceeds a higher quantile prediction (e.g., $q_{10} > q_{50}$). We avoid this by post-processing outputs via sorting across generated quantiles.Cold Start: Occurs when predicting demand for a new store or item without historical data. We avoid this by using a single global model trained on aggregate item family and store attributes.Overfitting: Occurs when a model learns training noise instead of general patterns. We avoid it by using early stopping and validating strictly on future time blocks.Phase 3: Deep Learning & ML vs DL Comparison (Nov 25 - Dec 1)Aim: Implement a simple deep learning model (small MLP or LSTM) under a strict time budget and compare performance against gradient boosting and the naive baseline.Why: Fulfills capstone course requirements to evaluate deep learning while maintaining a practical fallback if training time proves excessive.Outputs: Deep learning model scripts, walk-forward evaluation comparative metrics, and an honest final evaluation writeup in notes/results.md.Pitfalls & Prevention:Deep Model Losing to Gradient Boosting: Deep learning models often underperform gradient boosted trees on tabular retail datasets. We avoid project delays by setting a fixed training time budget and accepting a fair loss for deep learning as a valid, publishable finding.5. GitHub Guide and RulesCore GitHub ConceptsRepo: Short for repository; a centralized storage space where all project source code, documentation, and history are stored.Board: A kanban-style visual interface with columns (To do, In progress, Review, Done) used to track task progress.Branch: A parallel, isolated copy of the repository code where a developer can safely make and test changes.Pull Request (PR): A formal proposal to merge code changes from a working branch into the main repository branch.Issue: A dedicated tracking item representing a task, bug, or feature request logged on GitHub.Repository RulesThe main branch is strictly protected: no direct pushes allowed. Authors cannot approve their own PRs.Each task corresponds to one GitHub Issue containing: Task ID, Goal, Why, Steps, Done when, Size, and If stuck.Notebooks: One owner per notebook. GlossaryEDA (Exploratory Data Analysis): The process of analyzing datasets by summarizing their main statistical characteristics and visual patterns.Feature: An individual measurable property or variable used as an input to a machine learning model.Lag: A historical value of a variable from a previous time step used to predict future trends.Leakage (Data Leakage): An error where information from outside the training dataset (such as future data) is inadvertently used to train a model.Time Split: A method of dividing time series data into training and testing sets based strictly on chronological order.Baseline: A simple reference model (e.g., predicting last week's sales) used to establish a benchmark for complex models.Quantile: A statistical boundary dividing a probability distribution into intervals, representing forecast uncertainty intervals (e.g., $q_{10}, q_{50}, q_{90}$).Walk-Forward: An evaluation technique for time series where a model is trained on past data, tested on the next future block, and repeatedly shifted forward in time.PR (Pull Request): A request to review and merge code changes from a feature branch into the main codebase branch.Branch: An independent working line of development inside a Git repository.Issue: A tracked task item or bug report within a GitHub repository project board.12. FAQ for Confused BeginnersQ1: What do I do first?A: Complete Task T2 by creating a branch, adding your practice file in team/, opening a Pull Request, and getting it merged to confirm your GitHub workflow setup works.Q2: What if I break something in code?A: Don't worry! You are working on your own separate Git branch. Main code cannot break because direct pushes to main are blocked. You can always undo local changes or ask for help.Q3: Where should I store project data files?A: Never store data on your local hard drive or upload data to GitHub. All shared raw and interim datasets live in our dedicated shared Google Drive folders defined in src/config.py.Q4: Can I run modeling experiments directly inside Jupyter Notebooks?A: Yes, notebooks are great for initial data exploration and visual experiments. However, any core reusable functions (data cleaning, metrics, models) must be converted into .py scripts inside src/.Q5: What happens if my assigned task is blocked by another task?A: Flag the issue during our weekly sync or post a comment directly on your task's GitHub Issue. The project leader will reassign tasks or pair you up to resolve the blocker.Q6: How do we choose between LightGBM and Deep Learning if they disagree?A: We report the comparison honestly in notes/results.md. If LightGBM achieves lower error or trains significantly faster, LightGBM remains our primary forecasting model.Q7: Who merges my Pull Request once it is submitted?A: One teammate or the leader reviews and approves your PR (you cannot approve your own). The leader checks every PR. After approval, the author clicks Merge.13. Version HistoryVersionDateWhat Changedv1Nov 2026First initial release of ReStock AI Project Playbook.
